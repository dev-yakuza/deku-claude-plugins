# Herald Plugin

Claude Code のための**リポジトリ専用の編集組織**。Herald はリポジトリに執筆ハーネスを導入し、
そのリポジトリに特化した役割エージェントのチームがトピックを企画し、
`brief → research → draft → critique → verify → publish` の流れで専門的なブログ記事を書き、
PR レビューを経て公開し、実際の利用の痕跡からガイドを育てます。

> 姉妹プラグイン [Guild](../guild-plugin)(ソフトウェア開発)と同じ構造 — ハーネス、役割の骨格、
> 産出する内側ループと成長する外側ループ — を執筆に適用したものです。

[English](./README.md) · [한국어](./README.ko.md)

## コンセプト

- **目的** — サービス・アプリの宣伝。最終指標は CTA クリック・流入で、検索露出は手段です。
- **正確性は床** — Herald の公開経路では `verify` を通過していない本文を公開しません(人が修正した
  本文を含む)。床の上では 検索露出 > 読者価値。
- **骨格の役割** — 編集長(メインセッション)、コンテンツ企画、リサーチャー、ライター、
  ファクトチェッカー、編集者。**条件付き** — 分野専門家・監修者、検索・発見担当(SEO・AEO・GEO)、
  イラスト、翻訳、配信・SNS。
- **外部監査者** — 組織の外にいるペルソナなしのレビュアーが、編集者の PASS の後(記事ごとに最大 3 ラウンド、2 ラウンド目からは
  BLOCKER・未修正の指摘・回帰だけを止め、残りは PR へ)、また流れの外
  (`/hrd review`)でも確認します。
- **公開 = `/hrd ship`** — PR ごとの承認、人の修正の再検証、マージ、デプロイ、URL 確認、記録。
  書くだけでは何も公開されません。

## インストール

```bash
claude /plugin marketplace add dev-yakuza/deku-claude-plugins
claude /plugin install deku-claude-plugins@herald-plugin
```

必要環境: `git` 2.38 以上、認証済みの `gh`、`python3` 3.9 以上。batch は `claude` CLI。
Search Console(任意): `pip install google-auth requests`。

## クイックスタート

```bash
/hrd init            # リポジトリ分析 + インタビュー → ハーネス(コミット前に確認)
/hrd plan            # トピッククラスターをキューへ
/hrd write t0001     # 記事 1 本 → PR、PR まで質問なし
/hrd write t0001 --attended  # 同じ流れで各ゲートで確認し、PR の前に承認
/hrd ship            # PR 承認 → 再検証 → マージ → デプロイ → URL 確認 → 記録
/hrd next            # 記事 1 本を公開まで一度に(キューが空なら plan から)
/hrd batch --n 5     # 無人執筆。autonomy.publish=auto なら公開まで
/hrd status          # トピック・保留・メンテナンスフラグ
```

## コマンド

**設定** `init` · `config` · `update` — **執筆** `plan` · `write` · `brief` · `research` ·
`draft` · `critique` · `verify` · `publish` · `resume` · `batch` — **公開** `next` · `ship` · `review` ·
`refresh` · `translate` — **SNS** `social`(`--setup` `--add` `--refresh` `--edit` `--persona` `--remove` `--list`、下書き: `social <sns> <slug>`、`social <sns> --daily`、`--final`) — **状態** `status`(`--requeue` `--drop` `--withdraw` `--withdraw-lang` `--unwithdraw` `--move`
`--release-slug` `--mark-published` `--unlock`) — **成長・点検** `evolve` · `rollback` · `audit` ·
`monitoring` · `ask` · `contribute`(未対応)。詳しくは `/hrd help`。

## 安全

- **INV1** 変更の適用は常に人の承認。無人実行は approve モードでマージせず、監査者の BLOCKER を
  却下しません。**INV2** 検証を弱めない(基準・ゲート・模範記事・床)。**INV3** すべて可逆
  (git、`/hrd rollback`)。**INV4** 追加的で、ローカルの進化を上書きしない。**INV5** サニタイズ
  なしにマシンの外へ出さない。**INV6** 抽出したルールは draft から始まる。
- **PreToolUse ガード**(`.claude/herald/scripts/guard.py`)が基準ファイル・批評/検証ペルソナ・
  保護設定キー・検証台帳の編集、マージ、デプロイ、範囲外コミットについて、人に確認(対話)または
  ブロック(無人)します。トリップワイヤであって境界ではなく、`/hrd audit` が事後に点検します。ガードが
  例外で落ちても起動できなくてもマージ・デプロイの前には確認しますが、hook の制限時間(30 秒)で打ち切ら
  れると何も決められません — 0.20.0 から settings 自体は `gh pr merge` の前に確認しません。
- **検証台帳**(ローカル)と**デプロイ前の整合性チェック**が、デプロイ前に base のすべての Herald
  記事を検証済みの内容と照合します。

## シーン画像 (0.18.0)

`images.scenes`(`/hrd config images`)があると、画像の場所を**シーン**にできます — 実在である必要の
ない状況(入国審査カウンターの旅行者)で、実在の人物・場所・商標・作品は描きません。limner が
**Qwen-Image-Edit-2511(4bit)+ Lightning 8step**(Apache-2.0、script2video とモデル保存先を共有、
`lmn setup` 約 54GB)でこのマシン上で生成します。M2 Max 64GB で 1 枚 2〜3 分ほどかかるため、編集長が
limner の分離ワーカーを起動して短い呼び出しで確認し、`wait_minutes` を超えたら保留
(`tooling: limner …`)、`/hrd resume` が同じ実行を引き継ぎます。シーンには**文字がなく**(Herald が
英語のプロンプトに「文字なし」の固定文を付ける)、本文では画像の横に必ず **AI 生成の表示**が付きます
(`images.figure.scene` の `{label}` — 同じ slug のすべてのトピックで draft・verify・公開時に、
リポジトリの検査器とは別に確認し、trim では消えない)。illustrator が先に画像をレビューし、draft を
通すには**すべてのシーンを人が確認**する必要があります。判定は state のフィールドではなく生成台帳と
確認台帳が行うので、未確認の画像はリモートに出ません。limner・モデル・RAM がなければシーンだけが
オフになり、翻訳リポジトリではオフです。

## SNS の形式 (0.19.0)

`/hrd social <sns> <slug> --format image|cards|comic`(`--daily` も)で投稿に画像を付けます:**画像 1 枚**、
**カードニュース**(表紙・要点カード 1〜8 枚・最後のカードのカルーセル)、**漫画**(2×2 または 3×2 の 1 枚、
run ごとに下書き 1 つ)。すべての画像は Herald の定数のレイアウトから limner が合成します — 文字をモデルが
描くことはなく、漫画のコマは文字なしで生成してから吹き出し・キャプションを合成します。素材はその記事の図解・
limner の OG・人が確認したシーン(コミットされたとおり)と、この下書きのために生成した画像だけで、引用・外部
画像と同じバイトは決して出ません。画像の中の文字は投稿本文と合わせて検査し(統計・サービス体験・引用、
サービスに触れれば広告として判定)、生成画像を含む投稿には必ずチャネルの **`ai_disclosure`**(本文の文言
またはプラットフォームの AI ラベル設定、広告表示とは別)が付きます。`check`・`close` は画像ごとに保護された
limner の compose 記録(出力・すべての入力画像・仕様から作り直したレイアウト)と照合し、人が承認する画像が
Herald の検査した画像であるようにします。`--final` は承認時のプロフィールと AI 表示を引き継ぎます。
`formats` のないガイドはテキストのみです(`/hrd social --refresh <sns>` が形式を調査)。

## `--ship` で最後まで (0.20.0)

`/hrd write <id> --ship`(`resume`・`refresh`・`translate` の `--ship`、`/hrd next` も)は、その記事
1 本を**人が見ずに**公開してほしいという人の依頼です。人が外部画像・引用・シーン・自動スクリーン
ショットを確認していた場所は、**新しい illustrator の spawn がレビュー**し、Herald が `--agent` で
確認します — 人の確認とは区別して残り(台帳の `by: agent`、PR 本文の `agent-reviewed (no human
look)`、ship の報告、`published.json` の `agent_confirmed`)、そのトピック・その場所・その内容にだけ
有効です。その後 PR は質問なしでマージ・デプロイされます: `HRD lock ship-pass` が PR head を確認し
直し、guard は検証済みの `gh pr merge … --match-head-commit <sha>` と設定されたデプロイ文字列にだけ
`allow` を返します。フラグの唯一の根拠はチェックアウトロックの印(guard が保護)なので、人が書いた
ときだけ付けます。欠陥は今まで通り PR で止まります — 開いた・延期した・エージェントが却下した
BLOCKER、変わった critique・verify ファイル、誰も保証していない PR 内のファイル
(`images-unconfirmed`)、人しか撮れないスクリーンショット、レビューが問題を見つけた撮影、1 日の上限。
batch と `--ship` なしの実行は変わらず、`/hrd update` が `gh pr merge` の前に確認していた 0.19.0 の
settings ルールの削除を提案します(guard 自身が確認します)。
