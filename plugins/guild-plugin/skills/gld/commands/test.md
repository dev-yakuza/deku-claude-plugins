# TEST (stage)

**Stage: test.** Role: **tester** (leader judges completion). Runs the tests, enforces the **verify gate** (raw evidence, not self-report); the leader judges automated-correctness completion and **advances to the QA stage** (test no longer marks `done` — QA does). Invocable directly (`/gld test <issue>`) or via `/gld dev`.

`$1` = Issue number. Returns a Section D line.

> **Bash**: `_bash_rules.md`. State/handoff: `_handoff.md`.
> **Output language**: all human-readable output in `config.language` (`_handoff.md` Section K); sub-agent prompts carry that instruction.

---

## Step 0 — Preflight

As the leader, follow `_preflight.md` **Medium tier**. If `.claude/guild/config.json` is absent → `FAIL: Guild not initialized (run /gld init)`. Load the test cases (`docs/specs/$1/test-cases.md`), the design output, and any execute-stage evidence (`<!-- guild:test-evidence:step-1 -->`). Load `docs/standards/verification.md` for the verify rules + DoD.

**Visual decision (no extra call — from what this step already loaded plus `config.json`; `_handoff.md` Section L):** `VISUAL_CASES = yes` when `test-cases.md` carries a `<!-- guild:visual-cases -->` section — coverage (L.2) is then checked whatever runs them. `VISUAL_RUN = yes` when `visual.runnable` is `true`, `commands.vrt` is non-null, **and** either `VISUAL_CASES = yes` or the execute ledger's first line reads `run: yes` (the branch touched a visual package — a refactor or debug fix can break a picture no visual case names) — the separate visual command runs. (Visual tests that `commands.test` already runs — `vrt` null — are covered by the normal run.) Hold the `<!-- guild:visual-baselines -->` block from the execute evidence, when present, for Step 2.

Validate `$1` is an Issue. **Read current labels first** (its own Bash call): `gh issue view $1 --json labels --jq '[.labels[].name] | map(select(startswith("guild:")))'`.

**Stage-start mark (right after the label read above, its own Bash call — after the Guild-initialized check and the Issue validation, so an uninitialized repo or an invalid Issue writes nothing; a later guard's refusal leaves only a mark file in the gitignored memory dir, which the next run overwrites):** `python3 <<SKILL_DIR>>/commands/atoms/capture_signal.py --mark --issue $1 --stage test`. **Every return in this file after this line** runs the capture reconciliation immediately before returning, after every capture that step makes (`_signals.md` Section C, *Capture reconciliation* — `--stage test --since auto`).

**Split-parent guard** (right here, before any other work): if that read contains `guild:children`, refuse — a parent at `guild:children` is in an *orchestration* state, not a stage (`_handoff.md` Section A: a parent never carries both `guild:children` and a stage label at once), so Step 3's transition would destroy the link `dev.md` Phase 2b uses to drive the children:
```
>>> RESULT <<<
FAIL: #$1 is a split parent (guild:children) — its work is its children's, not its own. Run `/gld dev $1` (or `/gld resume $1`) to drive the children.
```
(`guild:child` is **not** this case — a child legitimately carries `guild:child` + its stage label and proceeds normally.)

Empty → add `guild:test`. Non-empty → do not add on top (Step 3's transition removes whatever **stage** label was actually found here, not necessarily `guild:test` — never `guild:child`, a permanent identity marker a child Issue also carries alongside its stage label; `_handoff.md` Section A). Ensure the Issue's branch is checked out (the one implement created).

## Step 1 — Spawn tester (run + verify)
Spawn the tester sub-agent:
- `subagent_type`: `general-purpose`, `model`: the role file's `model:` frontmatter (`_model_tiering.md` Section 0 — `sonnet` when absent), `description`: `tester verify #$1`
- `prompt`:
  > Adopt the persona in `.claude/agents/tester.md`. Execute the tests for Issue #$1 on the current branch — run the project's test command (unit + existing suites; E2E/manual QA are later milestones in M1). **Capture the raw runner output**. ⚠ **Run the suite in the FOREGROUND with an explicit `timeout` (up to the value of `printenv BASH_MAX_TIMEOUT_MS`, or 600000 ms when it is unset — the unattended launchers raise it to 3600000), never `run_in_background`** (`_bash_rules.md` — *Long-running commands*): a full suite commonly outruns the Bash tool's 120 s default, and a backgrounded one is killed when your turn ends, so the evidence you are here to capture never arrives. A run killed at that ceiling is a failed run, not a pending one: report it as not green and name the test or file that was running when it was killed (a change that makes a test hang is a defect, not slowness) — never detach the suite to get around the ceiling. Confirm every acceptance-criterion test case from `docs/specs/$1/test-cases.md` is covered and passing. ⚠ **Read that file whole, in one Read.** You are confirming *every* acceptance criterion, so a case you did not read is one that passes as covered without anyone looking — and "all covered" is what clean work looks like, so the failure is invisible. The Read tool returns up to 2000 lines without saying when it stopped: compare the last line number against the file's length and page from there if they differ. Verify gate: your pass claim MUST match the raw output — if they disagree, the raw output wins and you report the failure honestly. Do NOT weaken/skip tests to pass (INV2). **Honesty-of-scope (mandatory)**: explicitly declare WHAT you ran (with raw evidence) AND WHAT you did NOT run — specifically `commands.e2e` (integration/E2E) and manual QA / the human's visual judgment are NOT executed in M1 (an automated golden/VRT run, when you ran one, is something you DID run — list it with its evidence). Never phrase your result as "fully QA'd" or "all problems verified" — the accurate claim is "automated tests (what you ran) pass and the written AC are test-covered."
  > **Visual tests — `VISUAL_CASES = <yes|no>`, `VISUAL_RUN = <yes|no>`, `commands.vrt = <literal or null>`, `visual.env = <literal>`** (the leader substitutes all four). When `VISUAL_RUN = yes`, run `commands.vrt` after the test command — same foreground/timeout rule, same raw-output capture; an array is run step by step, one call each from the repo root, stopping at the first failure. Coverage needs the runner to name each test it passed: when its summary only counts files (Vitest's default non-TTY reporter), add the runner's verbose reporter flag (`--reporter=verbose`) to whichever command runs the visual cases (`commands.vrt`, or `commands.test` when visual tests run inside it) — **a reporter flag is the only change you may make to the command** (a flag like `--ignore-snapshots` or `--update` would pass without comparing). When `VISUAL_CASES = yes` (whichever command ran them): every row of the `<!-- guild:visual-cases -->` section must be covered per `_handoff.md` Section L.2 — a row without a comparing test that passed (and, when `visual.baselines` is non-empty, without its committed expected image) is **uncovered**, exactly like an AC with no test. On a visual failure, report the diff/actual image paths the runner wrote **only if they exist on this host** (a `docker compose run --rm` without a mounted output dir leaves them inside the container — then say so), and judge Section L.5: outside `visual.env`, or uniform rendering noise on images this change cannot reach → report it as an environment suspect, not a regression. ⚠ **Never run a create/update/approve command** (`visual.create`, `--update-goldens`, `-u`, `--update-snapshots`, `reg-suit approve`) and never touch a comparison setting: this stage proves correctness, and rewriting the expected image to match is the visual form of deleting an assertion (INV2, Section L.4). A red visual test is red.
  > **Risk-based E2E judgment (mandatory — not a blanket skip)**: M1 does not auto-run E2E, but you MUST still JUDGE whether this change warrants E2E regression, and state it: (a) **contained / low-risk** (local widget/util fix, no cross-screen flow or integration change) → "E2E 불요: <one-line reason>" — a *justified* skip; (b) **touches flows / navigation / integration / data sync** → "**E2E 회귀 실행 필요: `<suite>`** — M1 자동 미실행이므로 사람이 실행해야 합니다" — hand it to the human. ⚠ **The two branches are a binary and must be worded symmetrically: `E2E 불요` / `E2E 회귀 실행 필요`.** Never soften branch (b) to "권장/가능하면/여유되면" — the whole point of the judgment is to tell the human whether they must run it, and a hedged (b) is read as "no" by every reader in a hurry. Softness is not how you express uncertainty here: if you are unsure the change touches a flow, that IS branch (b). Base the judgment on the diff's scope + the hotspot list, not on convenience.
  >
  > <!-- guild:result-contract -->
  > Return EXACTLY one status line, preceded by a `>>> RESULT <<<` sentinel on its own line. Anything before the sentinel is ignored. Status is one of `DONE` / `DONE_WITH_CONCERNS: <one-line>` / `BLOCKED: <one-line>` / `NEEDS_CONTEXT: <one-line>` / `FAIL: <reason>`. **Artifacts are passed as files, not pasted** — write to the working tree or `docs/specs/<issue>/` and name the path in the RESULT line; never inline an artifact body into it.
  > <!-- /guild:result-contract -->
  > Include the raw test summary line. Write output in `config.language`.

## Step 2 — verify gate (leader, mandatory)
As the leader, enforce the verify gate (`_handoff.md` Section E):
- Post the tester's raw runner output as evidence under `<!-- guild:test:output -->` … `<!-- /guild:test:output -->` (temp-file pattern), including the pass/fail summary and AC coverage.
- **Verification scope declaration (mandatory, honesty-of-scope)**: the output MUST have an explicit **검증 범위** block stating (a) what ran with evidence (e.g. `flutter test` unit, `flutter analyze`, golden — and `commands.vrt` when `VISUAL_RUN = yes`), (b) **what did NOT run — `commands.e2e` (integration/E2E) and the human's visual judgment** (an automated visual comparison proves the screen matches its baseline, not that the baseline is right — that judgment is the human's at the PR's visual-changes section, and the designer's at QA), (c) **the `<!-- guild:visual-baselines -->` block copied verbatim** from the execute evidence (`_handoff.md` Section L.3 — QA and review read it from here; omit only when the repo has none of `visual.baselines`, `visual.tests`, `visual.config_files` and `commands.vrt` is null — the same condition the execute ledger is written under), plus on a visual failure the diff image paths that exist — and when visual tests exist but `visual.runnable` is not `true`, say so in (b): "`commands.vrt` 미실행 — `<visual.env>` 에서만 재현, CI/사람이 실행" (a UI change should not first meet its goldens on CI), and (d) the **risk-based E2E judgment** — either "E2E 불요: <reason>" (justified skip for a contained change) or "**E2E 회귀 실행 필요: `<suite>`** (사람 실행)" (change touches flows/integration) — one of those two strings, never a hedged third wording. A blanket silent skip is NOT acceptable — there must be a judgment. This makes "verify 통과" clearly mean *automated-test verification with a stated E2E risk call*, never "fully QA'd". Reject any output missing this block.
- Cross-check the tester's claim against the raw output. **Complete only on matching raw evidence.** If they disagree → the raw output wins; this is not done.
- Check the Definition of Done from `docs/standards/verification.md`.
- **Ground-truth capture (①, `_signals.md` Section C):** if the tester's claim **disagreed** with the raw output (a verify-gap), OR verify failed (tests red / AC gap), append one entry (its own Bash call). `--surprise` when a claimed pass was actually red (a confident self-report contradicted by evidence — the strongest ranking lever):
  ```bash
  python3 <<SKILL_DIR>>/commands/atoms/capture_signal.py --kind verify-gap --issue $1 --stage test --role tester --area "<the area under test>" --summary "<claimed vs raw / AC gap, 1 line>" --evidence "<raw runner summary line>" --surprise
  ```
  **Skip** when raw evidence matched the claim and was green — no gap means nothing to learn (agreement ≠ signal).

## Step 3 — Judge completion + return

**Capture reconciliation immediately before each return line below** — after the stagnation guard and its capture, not before them (`_signals.md` Section C, *Capture reconciliation* — `--stage test --since auto`): recorded < owed → backfill the missing captures now.
- **Visual-case coverage** (only when `VISUAL_CASES = yes`): a visual case that is not covered per `_handoff.md` Section L.2 is an **uncovered AC** for the guard below — loop back, do not pass it.
- **Visual failures** (any golden/VRT failure, whether from `commands.vrt` or inside `commands.test`): **verify failed** like any red test; never treated as "only visual". **Except pending regeneration**: failures confined to images the ledger lists as `P` are expected — those images were declared un-regenerable here — so return `NEEDS_HUMAN: <n> images pending regeneration in <visual.env> — <paths>` (unattended: `guild:needs-human` + comment, `OK PAUSE: needs-human — pending regeneration`) instead of looping the developer. **Except an environment suspect** (Section L.5 — also when `visual.runnable` is `false` and goldens ran inside `commands.test` anyway): return `NEEDS_HUMAN: visual failures look environmental — <visual.env> vs <this host>; <n> images` (unattended: `guild:needs-human` + comment, `OK PAUSE: needs-human — visual environment`) instead of looping the developer — a developer loop on rendering noise ends in rewritten images.
- **Vacuous-test guard FIRST (INV2 spirit — #894 lesson) — apply before judging "verify passed" below, never after**: before accepting "AC covered", confirm the covering tests are **effective** — a test that passes but asserts nothing meaningful, or whose assertion does **not** react when the code-under-test breaks (the #894 disabled-contrast pattern: `meetsGuideline` skipped its check in the disabled path, so it passed regardless), is **not** coverage. If verify leans on a vacuous test, treat that AC as **uncovered** → loop back for a real assertion (do not proceed to the "Verify passed" bullet below for that AC). A green suite of vacuous tests is not a pass.
- **Verify passed** (raw evidence green + AC covered **by the guard above, not vacuously** + DoD met) → advance to the **QA stage** (holistic quality follows automated correctness). Remove **whatever `guild:*` stage label Step 0 actually found** (substitute in place of `guild:test` below if it was something else; **never remove `guild:child`** if present). **Also remove `guild:needs-human` in this same call if Step 0's label read found it present** (`_handoff.md` Section A):
  ```bash
  gh issue edit $1 --remove-label "guild:test" --add-label "guild:qa" --remove-label "guild:needs-human"
  ```
  **Verify this edit landed** before returning (`_handoff.md` Section F — `gh` write failures): re-read the labels; a failed edit means the Issue is still at `guild:test`, so returning `OK ADVANCE: qa` would desynchronise the state model.
  Return:
  ```
  >>> RESULT <<<
  OK ADVANCE: qa
  ```
- **Verify failed** (tests red — a suite killed at the Bash timeout ceiling counts as red: a slow suite and a test the change made hang look identical, and the hang is a defect; a recurring timeout reaches the human through the stagnation guard below, where the timeout itself is the blocking signature whichever test was last running — or evidence contradicts claim, or AC gap) → do NOT mark done.
  - **Attended**: return `NEEDS_HUMAN: tests not green / AC gap — <one-line>; loop back to execute?` (the leader/human decides whether to loop back to `/gld implement $1`).
  - **Unattended** (`GLD_UNATTENDED=1`, `_handoff.md` Section H): before each loop-back, apply the **stagnation guard** (`_stagnation.md`) — the same test(s)/AC gap recurring after a loop-back → escalate immediately (`OK PAUSE: needs-human — stagnant loop-back — <reason>`, `--kind stagnation` capture) rather than consuming the remaining attempt. Otherwise the leader auto-decides — bounded loop-back to execute (≤2 attempts); if still failing, add the **`guild:needs-human` label** + a `<!-- guild:needs-human -->` comment stating the gap, and return `OK PAUSE: needs-human — tests not green / AC gap` (do NOT transition the stage label). **Never weaken/skip tests to pass** (INV2). Detect mode via `printenv GLD_UNATTENDED`.
  ```
  >>> RESULT <<<
  NEEDS_HUMAN: tests not green / AC gap — <one-line>; loop back to execute?
  ```
- Hard error → `FAIL: <reason>`.

## Note — test hands off to QA
`test` proves **automated correctness** (unit/existing + golden/VRT + analyze, cross-checked against raw evidence — a visual comparison proves "matches the baseline", and whether the baseline itself is right is judged by the designer at QA and the human at the PR); it then advances to the **QA stage** (`guild:qa`) for holistic quality. `test` no longer marks `done` — the QA stage does, after its risk-based quality pass. So the `test` output should be scoped as "automated correctness verified; holistic QA follows" — never imply full QA here. The guided-review nudge fires at `done` (QA stage — `qa.md` owns it, both on direct `/gld qa` invocation and via `/gld dev` Phase 3), never here — `test` only ever advances to `guild:qa`, it doesn't reach `done` even on a direct `/gld test` invocation, so there is nothing to nudge yet at this stage.

## Hard rules
- **Verify gate is the concrete `_handoff.md` Section E check** — raw runner output is the only accepted proof of green.
- **No verification weakening** (INV2) — including never rewriting a visual baseline to make a visual test pass.
- Read-only against source (test runs the suite; it does not modify implementation — fixes go back through execute).
