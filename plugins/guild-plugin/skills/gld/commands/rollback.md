# ROLLBACK (on-demand — safe revert of a Guild-authored change)

**Undo a Guild change with git — never destructively.** The human's escape hatch (INV3). Reverts are **additive** (`git revert` creates an undo commit; unmerged work is closed; a stage is relabeled) — **never** `reset --hard`, force-push, or history rewrite. Everything stays recoverable.

`$1` = what to undo: a **PR number**, a **commit SHA**, or the literal word `stage` (move an Issue back one stage). When `$1 == "stage"`, `$2` = the **Issue number** to move back — per `SKILL.md`'s routing (`$1`, `$2`… are space-separated tokens passed positionally), `/gld rollback stage 42` arrives as `$1="stage"`, `$2="42"`; there is no single two-word `$1`.

> **Bash**: `_bash_rules.md`. State/handoff + owner/repo: `_handoff.md`.
> **Output language**: all human-readable output in `config.language` (`_handoff.md` Section K).

---

## Process
**0. Preflight** — as the leader, confirm Guild is initialized; resolve `<owner>/<repo>` (`_handoff.md` Section F).

**1. Identify the target**
- **`$1` is a PR number** (call it `<p>` below) → `gh pr view <p> --json state,mergedAt,commits,headRefName,baseRefName,mergeCommit` — merged vs open, its commits/branch. For a merged PR, first make its own commits and today's base local — its own Bash call, `git fetch origin pull/<p>/head <baseRefName>`. Its **evolve runs** are the commits whose `messageHeadline` **starts** `chore(guild): evolve #` + a run number + ` —` (any number — not `<p>`), leaving out any that end `— 0 changes applied` (nothing to undo).
  - **None** → if the PR's commits were all `— 0 changes applied` runs, there is nothing to undo: say so and stop. Otherwise it is an ordinary PR: a merge commit (`git rev-list --parents -n 1 <mergeCommit.oid>` prints three hashes) is reverted with `-m 1`; with two hashes (squash or rebase — GitHub's `mergeCommit` cannot tell them apart) revert the PR's commits by their `oid`s from `commits`, newest first, which is right for both. If one of them is a `— 0 changes applied` run, keep the ledger files as in step 3 (no note: nothing was applied).
  - **One or more** → undo **only the runs**, never the whole PR: one run → that one; several → ask the human which, and undo each chosen run newest first with its own note. Revert the run's commit by its own `oid` from `commits` — that works however the PR was merged (merge, squash or rebase: git applies the run's inverse to today's tree). Find each run's entry as in step 1.2 below and use step 3's ledger-keeping sequence; step 2's plan names each commit being reverted.
- **`$1` is a commit SHA** → `git show --stat <sha>` — the commit + its diff summary. **Check whether this commit is an evolve-applied change** — if it is, reverting it (step 3) must also update the ledger entry (see below), not just the git history. ⚠ **Do not grep `evolution-log.md` for the SHA**: a run's ledger entry is written *inside* the run's own commit (`evolve.md` Phase 6 step 7), and a commit can never contain its own hash, so the SHA is not there and never will be. Match on what the entry actually carries:
  1. Read the commit's subject (its own Bash call) — a subject ending `— 0 changes applied` is a run that applied nothing: there is nothing to undo, so say so and stop here, before step 2: `git show -s --format=%s <sha>`. An evolve run commit's subject is `chore(guild): evolve #<n> — <k> changes applied`.
  2. If the subject **starts** `chore(guild): evolve #<n> —` (anchored like `_model_tiering.md`'s window grep: rollback's own `Revert "chore(guild): evolve #…"` must not match — redoing a rollback is then a plain revert, which re-applies the run and removes the `[reverted]` note in one step; if a later evolve run has since moved that entry to the archive, the redo conflicts on the ledger — resolve it by keeping the ledger and deleting the note by hand), find that run's entry — its own Bash call, `python3 <<SKILL_DIR>>/commands/atoms/ledger.py where <n>` prints its `file:start-end` (exit 2: found under a heading not in the run shape — use that range all the same), which may be `.claude/guild/evolution-log.archive.md` (evolve moves old runs there); Read that range, never either file whole. Two ranges (two branches each ran that number) → **first, the entry that commit added itself**: `git show <sha> -- .claude/guild/evolution-log.md` (its own Bash call; on the PR path `<sha>` = the run's `oid`) — the entry whose `applied-onto:` value equals the one on that diff's `+` lines (the entry's text survives a rebase, while the commit's parent does not — `evolve.md` Phase 6 step 7). Only when that settles nothing (no such `+` line), the entry is the one whose `applied-onto:` equals the evolve commit's parent (on the PR path, of the PR's `chore(guild): evolve #<n> —` commit from `commits` — its own Bash call after the fetch above, `git rev-parse <oid>^`, since `commits` lists no parents — not of `mergeCommit`). Its `applied-onto: <parent-sha>` field records the commit the run was applied on top of, so `<parent-sha>..<sha>` is exactly the run's change set (적용 시점 기준 — rebase 뒤에는 성립하지 않음).
  3. Any other subject → an ordinary commit; skip the ledger sync entirely. (A merge or squash commit — `Merge pull request #<p> …`, or a subject ending `(#<p>)` — may carry an evolve run inside it: run `/gld rollback <p>` instead, which finds and reverts only the run.)
- **`$1 == "stage"`** → `$2` is the Issue number; read its state + labels in one call and derive the stage with `_handoff.md` **Section A — canonical stage derivation** (it returns the one actual **stage** label — or `"none"` — plus the `paused`/`harness`/`child` flags for the non-stage kinds, so "the current label" is never assumed singular). Rollback needs `state` too (see the closed-`guild:done` case below), so add it to the same call:
  ```bash
  gh issue view $2 --json labels,state --jq '{state, stage: ([.labels[].name] | map(select(startswith("guild:") and . != "guild:child" and . != "guild:needs-human" and . != "guild:harness" and . != "guild:sprint")) | .[0] // "none"), paused: ([.labels[].name] | any(. == "guild:needs-human")), child: ([.labels[].name] | any(. == "guild:child"))}'
  ```
  Compute "one stage back" from `stage` **only** — never from `paused`/`child`, which are not stages. **If `child` is `true`**, also check its body for `Parent Issue: #<n>` and read that parent's current label: if the parent is already `guild:done` (Phase 2c integration already ran, per `_handoff.md` Section I), rolling this child back leaves the parent silently inconsistent — a "done" epic with a regressed child underneath, invisible to `status.md`/`monitoring.md` since neither re-checks a closed parent's children. This isn't a case rollback can fix by itself (re-opening/re-orchestrating the parent is a design-level call, not a revert), so **surface it explicitly in step 2's plan** ("parent #<n> already integrated as done — rolling back this child will not automatically reopen or re-flag it; you may want to also `/gld resume <n>` afterward") rather than silently proceeding as if the child were still standalone. Stage order (`status.md`'s convention): `analyze < design < execute < test < qa < done`. **Two labels are not in this ordinal chain and need their own handling, not a naive "previous row" lookup**: `guild:children` is an **orchestration state** (`_handoff.md` Section I), not a spine stage — rolling it "back one" is undefined; refuse with `NEEDS_HUMAN: #$2 is a split parent (guild:children) — rollback doesn't support orchestration state, target one of its children instead` rather than guessing. `guild:done` rolling back to `guild:qa` is well-defined *unless* the Issue was also closed (`_handoff.md` Section D notes a done Issue "may" be closed) — check `state` in the same `gh issue view` call, and if closed, reopen it (`gh issue reopen $2`) as part of the same confirmed action, stating that explicitly in step 2's plan. **`guild:analyze` is the other boundary** — it's the *first* row in the ordinal chain, so there is no predecessor `guild:*` label to move back to (a derived `stage` of `"none"` means *not started*, not a stage in the chain — `status.md`'s convention — so there is nothing to roll back there either); refuse with `NEEDS_HUMAN: #$2 is already at the first stage (guild:analyze) — there's nothing earlier to roll back to. To fully reset it, remove the guild:analyze label by hand instead.`

**2. Show the plan + PAUSE for confirmation (INV1 — rollback acts, so confirm first)**
State exactly WHAT will be reverted and the METHOD (which is always non-destructive):
- Merged PR / commit → **`git revert <sha>`** (new undo commit; opens a revert PR referencing the original). Merge-conflict on revert → surface, the human resolves; never force. If step 1 identified this commit as an `[applied]` evolve run (via its `evolve #<n>` subject tag), also state that the ledger is kept as it is and the entry is annotated `[reverted]` (below) so it stops reading as still-applied — a plain revert would delete the entry.
- Open (unmerged) PR → **close + delete its branch** (`gh pr close <n> --delete-branch`). The work is on the branch's history only (recoverable by reopening).
- `$1 == "stage"` → **relabel** Issue `$2` back one stage, using the derived `stage` from step 1 (never `guild:needs-human`/`guild:child`/`guild:harness`, which aren't stages): `gh issue edit $2 --remove-label guild:<cur> --add-label guild:<prev>`. Touch **only** that one label: `guild:child` is a permanent identity marker (stripping it would drop the Issue out of Section I's child-discovery query), `guild:harness` is provenance that outlives every stage, and if `guild:needs-human` was also present, leave it — rolling back a stage doesn't resolve the pause, and stripping it here would misreport an unresolved pause as clear. Note: the stage's *artifacts* (comments, commits) remain — this only moves the state pointer so the stage re-runs. `guild:children` target → refused per step 1 (not a stage). `guild:analyze` target → refused per step 1 (no predecessor stage). `guild:done` target on a closed Issue → the plan also states the reopen.
  **Loop-back record** (`_handoff.md` Section B): a stage rollback is a human relabel — it writes no `### loopback <n>` block and does not count against the cap. But when the target `<prev>` is `guild:design` or `guild:analyze` — the design is being redone, so the old loop-back history should stop counting — **and** the Issue has a `<!-- guild:loopback -->` comment **and** its last block is not already a `### loopback-reset`, the plan also says "loop-back count reset" and, after the relabel, step 3 takes a timestamp (`python3 <<SKILL_DIR>>/commands/atoms/capture_signal.py --now`) and inserts
  ```
  ### loopback-reset
  at: <that output>
  by: human
  ```
  just before `<!-- /guild:loopback -->` (the write rule in Section B). No comment → write nothing; never create one just to hold a reset. (`stage` moves one stage per call, so `execute → design` and then `design → analyze` are two calls; the "last block is already a reset" check keeps the second from adding another.)
Wait for the human's explicit "yes".

**3. Act (only after confirm; each its own Bash call)**
Execute the confirmed method. **An evolve run is reverted without its ledger** — the ledger is history, and a plain revert deletes the run's own entry (it ships inside the run's commit) and conflicts once that entry has moved to the archive: `git revert --no-commit <sha>` (a non-zero exit from a conflict is expected here — go on), then `git checkout HEAD -- <path>` for each of `.claude/guild/evolution-log.md` and `.claude/guild/evolution-log.archive.md` that exists at HEAD (`git cat-file -e HEAD:<path>`; this also clears a conflict confined to them — any other conflict surfaces as usual), then the ledger sync below, then `git add` it and `git commit --no-edit --cleanup=strip` (strip drops git's `# Conflicts:` lines from the message). If the commit is refused (the repo's pre-commit hook runs on it), nothing was committed: report the hook's reason and `git revert --abort`. For a `git revert`, push + open the revert PR (`Refs #<orig>`, body: what/why reverted). Report the new undo commit/PR.

**Evolve-ledger sync (only when the reverted commit was an `[applied]` evolve run, identified by its `evolve #<n>` subject tag per step 1):** append a note to that entry in the file step 1's `where` printed (Edit tool — do not delete the original entry, INV3 reversibility means the history stays intact) marking it with a line of its own, `[reverted <date> — by the commit that carries this note]` (at the start of the line, not quoted — `ledger.py` reads it only there); it lands inside the revert commit, which cannot name its own hash. Without this, `/gld audit` Dimension E and evolve's own regression-tracking (Phase 0 step 3 "prior-applied targets") would keep reading the ledger as if the change were still in effect after a human has explicitly undone it.

**4. Report** — what was reverted, the undo commit/PR link, and how to **redo** if this was a mistake (revert the revert / reopen the PR / relabel forward). Everything is reversible.

## Hard rules
- **Never destructive** (INV3/INV4): `git revert` (additive) only — never `reset --hard`, `push --force`, `rebase`, `branch -D` of merged work, or history rewrite. ⚠ The `branch -D` ban is **rollback's** — undoing must not drop the work it undoes. `/gld sprint retro` Phase 7 is the one exception, and only for a closed sprint's `MERGED` PR whose local tip equals the merged `headRefOid`: the commits stay on GitHub, so that deletion is reversible (INV3).
- **Confirm before acting** (INV1): show target + method, wait for the human. Read-only until confirmed.
- **Conflicts surface, never force** — a revert that conflicts is handed to the human.
