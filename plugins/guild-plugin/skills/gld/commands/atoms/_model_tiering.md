# MODEL TIERING (shared contract — dynamic tier escalation/de-escalation)

**Not a stage.** Defines Guild's model-tier policy (mechanical → Haiku, stage execution → Sonnet, hard judgments → Opus) with two dynamic mechanisms on top of the static per-role/per-task defaults (Section 0 says where those come from): (A) **immediate escalation** on a genuine execute-stage loop-back, local to one stage invocation, no persistence; (B) **default-tier review**, a periodic evolve-driven HITL proposal, symmetric with rule HR (`evolve.md` Phase 2 item "rule performance"). Read by `implement.md`/`debug.md`/`refactor.md` Step 4, by `evolve.md` Phase 2.5/Phase 2, and — Section 0 — by every persona spawn site.

The ladder: **haiku** (frugal — mechanical reads) < **sonnet** (standard — the default for nearly every role spawn today) < **opus** (frontier — hard judgment / an escalated retry). Guild has no tier above Opus and no per-repo persisted "trust" state (unlike a full runtime router) — both mechanisms below are deliberately simple: one bumps a single retry, the other is a human-approved proposal, not silent code.

---

## Section 0 — Where a role's default tier comes from

- **A persona spawn** — a sub-agent whose prompt says *"Adopt the persona in `.claude/agents/<role>.md`"* — runs at **that role file's `model:` frontmatter**. Every such spawn site says so instead of naming a tier. Before spawning, read the file's frontmatter (the Read tool, the first lines suffice) and pass that value as the Agent call's `model`. Accept exactly `haiku`, `sonnet` or `opus`. **No `model:` line** → `sonnet`, silently (a hired role's file may simply not carry one). **A value that is present but is not one of the three** — `inherit`, a full model id, a typo — also falls back to `sonnet`, but say so in the narration (`tech-lead.md model: <value> not a tier — using sonnet`) so a broken value is visible rather than silently ignored.
- ⚠ **Why the role file and not the command file.** The command files are the plugin's and change when the plugin is upgraded; the role file is the repo's own (`/gld update` does not touch its `model:`). Section C's default-tier review changes a default by editing a file, and before this rule the only file that named a tier was the command file — so the review either edited a field nothing read (the role file's `model:`, inert while every spawn said `sonnet` literally) or could not apply at all. Measured: in one repo `tech-lead`/execute was the top escalation group four evolve windows running, and the review that proposed acting on it found it could not — the spawn hard-coded `sonnet`. That is why the role file must be the source. (Under Section C's measure the same repo's windows read 2/6, 3/6, 2/9, 1/8, 3/10 — 12–50% — and would **not** trigger a raise: the developer's first attempt passed about 70% of the time. Those entries were filed under the reviewer; their target is the developer.)
- ⚠ **One file, every stage.** The role file is per role, not per stage: `tech-lead.md`'s `model:` drives its design skeleton, its execute conformance check and its sprint-plan review alike. A tier change proposed from one stage's trend changes all of them — Section C states that in the proposal.
- **Non-persona spawns keep the tier their command file states** — the execute-stage external auditor, the init scans, the readiness audit, evolve's panel lenses. They have no role file; nothing here changes them.
- `init` writes `model: sonnet` into every role file, so a repo that never edits one behaves exactly as before.

## Section A — Escalation on genuine retry (mechanical, local, no persistence)

Wired at `implement.md`/`debug.md`/`refactor.md` Step 4, **after** the stagnation guard (`_stagnation.md`) has already run and did **not** fire (i.e. this loop-back's reason genuinely differs from the prior attempt's — real, distinct feedback to act on, not a stall):

- **Attempt 1** always runs at the role's default (Section 0 — the role file's `model:`, `sonnet` unless the repo changed it). Trust the default first — do not escalate pre-emptively.
- **Attempt 2** (the retry within the bounded ~2-loop cap) runs **one tier above the default** for **every** role re-invoked in that retry — no exceptions and no narrower list: the developer, the tech-lead (whose conformance verdict must be about the redone diff, so it is always re-run), and **every 3.5b specialist/gate role the redone diff matches** — not only the one whose `BLOCKED` triggered the loop-back, since `_execute_spine.md` Step 4's chain rule re-derives that cast from the new diff and a redo can newly warrant a role that did not match before. The re-check must never be weaker than the redo. **The execute-stage external auditor re-scans on every loop-back** (`_execute_spine.md` Step 3.5a — not only ones it triggered), and its re-scan is bumped the same way — it has no persona and no default of its own to change, it simply re-runs one tier up for that retry. One rung up the ladder: haiku → sonnet, sonnet → **opus**. If a role's default was already Opus, it stays at Opus (no higher tier; this is not a failure).
- This is a **single-step, one-time bump for that retry only** — it does not compound across multiple loop-backs beyond the existing numeric cap, and it never persists past this stage invocation (the next Issue's execute stage starts back at the default).
- **Rationale**: attempt 1 failed for a real, distinct reason (not a repeat — the stagnation guard already ruled that out); giving the one bounded retry more capability is worth the one-time cost, and the ~2-loop cap already bounds total spend regardless.

State the escalation plainly in the re-invocation prompt/RESULT narration (e.g. "retry at opus — attempt 1 flagged `<reason>`") so it is auditable, not silent.

## Section B — Ground-truth tag (piggybacks the existing capture, no new event)

When Section A raises the **redone role's** tier for a retry — on the execute path, the developer's, i.e. whenever its default is below `opus` — tag the **same** ground-truth capture the loop-back already makes (`_signals.md` Section C) with `--escalated`. The reviewers re-run in that retry are bumped too, but the flag describes the role whose work was redone (Section C's target), so a developer already at `opus` gets no flag even though a sonnet reviewer was bumped. ⚠ Section A only fires *after* the stagnation guard did **not** fire, so the capture being tagged here is always a `correction` or a `verify-gap` — **never a `stagnation`**: a stagnant loop-back escalates to the human instead of retrying, so no tier was ever bumped and `--escalated` is dropped there (`_stagnation.md` Section C and `implement.md` Step 4 already state this; listing `stagnation` in the `--kind` set below would be a branch that can never be taken).
```bash
python3 <<SKILL_DIR>>/commands/atoms/capture_signal.py --kind <correction|verify-gap> --issue <N> --stage execute --role <role> --area "<area>" --summary "<...>" --evidence "<...>" --surprise --escalated
```
Substitute the **literal** Issue number for `<N>` (and every other `<…>`) before the Bash call — `_bash_rules.md` item 9. No new signal kind, no new capture point — `escalated` is one boolean field riding the loop-back entry that already exists. This is the only data Section C's evolve review needs; it costs nothing beyond a flag on a write that was happening anyway.

## Section C — Default-tier review (evolve-driven, periodic, HITL — symmetric with rule HR)

`evolve.md` Phase 2.5 computes a **model-tier scorecard** from data it already has — the ground-truth log and the merged-PR list — and Phase 2 proposes from it. The measure, the target, the bar and the follow-up are defined here once.

- **The measure — the first-attempt rejection share, per window.**
  - **Window**: from the previous evolve run's commit time — the committer timestamp of the commit whose subject starts `chore(guild): evolve #<n-1> —` (`evolve.md` Phase 0 step 3; anchored so a rollback's `Revert "…"` commit cannot match) — to now. The ledger header records only a date, which double-counts two runs on one day; the commit time does not. **First run** (no previous commit) → no window; the run's scorecard row is written with status `unmeasured` (it is `no-trend` anyway).
  - **Denominator**: the Issues behind PRs merged in the window — `scan_corrections`' `merged_prs[]`: each PR's closing Issues, or, when it has none, the Issue number in its branch name (`<type>/<N>-…`, the Guild branch convention); a PR with neither is left out — **restricted to Issues that went through Guild's spine** (a `docs/specs/<N>/` directory exists — one `ls docs/specs` call), so a hand-made PR with no execute stage does not dilute the share. `merged_prs` null or truncated → skip the scorecard for this run; never report 0%.
  - **Numerator**: of those Issues, how many have **at least one** entry in `scan_corrections`' `execute_rejections[]` (execute-stage `correction`/`verify-gap`, **any filing role, `auditor` included** — an auditor `BLOCKER` that changed code is a rejected developer attempt like any other) **at any time**, not only inside the window: an Issue's loop-back usually happens a run *before* its PR merges, and keying the numerator on entry time while the denominator keys on merge time would drop exactly those. Count each Issue once. Record both numbers and the share, plus the filing-role breakdown as detail — in the run's ledger row (`evolve.md` Phase 7 *Model-tier scorecard*), which every run writes with a status (`qualifying` / `small` / `unmeasured`); the bar and the follow-up below are read from that series.
  - ⚠ **Why a share of Issues and not a count of entries or of `--escalated` flags.** Entry counts grow with sprint size and with how many reviewers objected to the same attempt; a share of Issues does neither. And `--escalated` (Section B) is a bump marker only — it is set on every retried execute loop-back while the developer is below `opus`, so it carries no information about whether the bump fixed anything, and this test does **not** read it.
  - Entries of kind `stagnation` do not count: a stalled loop-back was not retried at a raised tier.
- **The target — the role whose output was redone**, not the role an entry is filed under. Execute entries are filed under the role that **rejected** the work (`--role tech-lead|security|auditor|…`, `_execute_spine.md` Step 4), while every execute loop-back sends the work back to the **developer** (Step 1). So the execute measure is about `developer`, and raising a reviewer would not change the attempt that keeps failing — it would only make every stage that reviewer runs in cost more. Keep the filing-role breakdown as supporting detail in the proposal.
- **The bar — propose a raise** when the share is **≥ 50% in each of ≥3 consecutive qualifying windows** — a *qualifying* window has a denominator of **≥ 3 Issues**; a smaller one is skipped, neither a pass nor a fail, and does not break the run of consecutive ones. A run with **no measurement at all** (no previous evolve commit found, `merged_prs` null or truncated) is treated the same way — skipped, does not break the streak, and does not count toward the follow-up's or the hold's 3 windows. 50% is a starting value, not a measured optimum — record the series so a later run can recalibrate it. ⚠ This ≥3-window bar is *stricter than*, not identical to, the base Axis-2 trend-unlock (`_data_sufficiency.md` Section A) — that gate only decides whether trend-dependent outputs run at all.
- **The edit**: the target's `.claude/agents/<role>.md` `model:` frontmatter (Section 0 — the persona spawns read it), **one rung above its current value** (haiku → sonnet, sonnet → opus); a role already at `opus` is not a subject. State the trigger in those words — *"the developer's first attempt was rejected in ≥50% of executed Issues for 3 windows"* — never as *"the higher tier is doing the real work"*: nothing measures that. ⚠ The file is per role, so the proposal must say which **other** stages that role runs in will move with it (e.g. `tech-lead`: design skeleton, execute conformance, sprint-plan review) — the human approves the whole effect, not just the stage whose measure triggered it.
- **The follow-up — whether it helped is measured, not assumed.** The ledger records the item with its target, the filing roles, and the share series before the change (`evolve.md` Phase 7). Once **3 qualifying windows** have passed since it was applied, compare the mean share of those 3 with the mean of the last 3 qualifying windows before it. **Not lower → propose reverting the raise** (one rung back down) through the same pipeline; this is the one de-escalation the hard rule below allows on that evidence alone. After a revert, do **not** re-propose the raise for the next **3 windows**, so the role cannot oscillate run to run. Until the comparison has its 3 windows, keep the item on the tracked list (`evolve.md` Phase 0 step 3's "last ~3 runs" does not drop it), and do **not** treat later execute loop-backs as panel-miss hits against it — loop-backs are expected to continue at a lower share, so a per-signal match would flag a raise that worked.
- **A low share** for many windows only **confirms** the current default is adequate; it is not by itself a reason to *lower* a default (there is nothing cheaper the spine uses for role spawns except haiku, which is reserved for mechanical/non-judgment work — do not propose moving a judgment role to haiku on clean-run evidence alone).
- Applied via the **normal HITL pipeline** (Phase 5 per-item approval) — a stated-default change is low-risk and reversible (INV3), but it is still a proposal, never a silent edit.
- ⚠ **Never propose a tier change for the execute-stage external auditor** (`_execute_spine.md` Step 3.5a). It is not a roster role (`_handoff.md` Section G), has no `.claude/agents/*.md` to edit, and its escalation is per-retry only (Section A). Its captures **do** count toward the developer's rejection share above — an auditor `BLOCKER` that changed code is a rejected developer attempt — but only as "this Issue had a rejection", never as a rate of its own: its `--role auditor` captures are deliberately capped to `BLOCKER`-and-acted-on entries (`_execute_spine.md` Step 4), so a per-auditor rate would not be comparable to anything.
- ⚠ **Never propose a tier change for `leader`.** The leader is not spawned as a sub-agent — the main session *embodies* it by loading `.claude/agents/leader.md` as a persona (`dev.md` Phase 0, and `leader.md`'s own description says so). Loading a file as a persona does not switch models, so that file's `model:` frontmatter is **inert**: the leader always runs at whatever tier the main session is running at, which Guild does not control. A "raise the leader to opus" proposal would edit a field nothing reads, and would then read as applied-and-working in the ledger. The field is kept only so the roster's frontmatter is uniform. The same applies to any future role the main session embodies rather than spawns.

## Hard rules
- **Never escalates on attempt 1** — the default is trusted first.
- **Never escalates past Opus** and never introduces a tier the harness doesn't have.
- **Never persists an escalation past its one retry** — Section A carries no state between stage invocations; only Section C (evolve, HITL) can change a *default*.
- **De-escalating a role's default below its current tier requires the same trend evidence in the opposite direction plus explicit human approval** — never automatic, never from a single clean run (avoids oscillation). **One exception**: reverting a raise that Section C's follow-up found did not lower the rejection share — that comparison *is* the evidence, it still goes through per-item human approval, and the 3-window re-proposal hold prevents oscillation.
- **Does not touch gate roles' pass/fail criteria** — escalation changes which model reviews, never what the review is allowed to approve (INV2 is untouched).
