**Mutation facts and commit messages** (`done_gate.mutations`, `done_gate.commits` of `in/leader-input.json`)

A criterion like "with this code removed the test fails" is not proven by a test that is green, nor by a role or a commit message saying "I removed it and it was red". The developer may have declared such changes in `mutations.json`; the engine then applied each one to a fresh tree of HEAD, ran the repository's `test` command, and `done_gate.mutations.rows` is what it saw — nothing in it is a role's claim except `find`, `replace` and `note` (what the developer chose to change).

- `killed` — the tests were red on HEAD with exactly that change, and green without it. This is the only status that is evidence, and only for the criterion the change really stands for: read `path`, `find` and `replace`, and check in `log_excerpt` (then `log_tail`) that the red is the test of that criterion failing on its assertion. A change that merely breaks the build, the import or every test proves nothing about the criterion; neither does one that removes something else than the criterion names. `control_flaky: true` means the tests were red once and then green on HEAD without any change: some test there fails on its own. The engine then counted a red only when the changed tree was red twice, each time with a failure line no unchanged run showed — still check that the failing test in the excerpt is the criterion's, not a timing or performance test.

How to read the two log fields of a row (both from the same run, the engine's copy of its output):

- `log_excerpt` — where the run FIRST failed. Its first line, `[gld engine] <log>, lines a-b of n: <rule>`, says how the engine found the place, knowing no test framework: lines with a failure word (fail, error, exception, assert, expected, …) that the green run without any change did not print; the first group of two or more such lines. The lines after it are numbered `N| `; `<tree>` is the engine's temporary copy of HEAD. Cut text ends with `…[truncated by the engine]`; the last line may list the numbers of the other failure-word lines. When the rule says no such line was found, the excerpt shows the first line the green run did not print, or nothing — then `log_tail` is all there is.
- `log_tail` — the END of the log (its last characters, `…[truncated by the engine]` in front when cut): the summary, and for `not-run` the engine's reason as the last line.
- A test run may stop at its first failure and close the tests still running: what such tests print afterwards (a test "closed", "did not complete", a summary that lists them) is the consequence of that first failure, not their own assertion. Judge the criterion by the first failure block; a later block is only evidence when it is an assertion of its own. Neither field is a verdict — the status is.
- `survived` — the tests stayed green with the code changed: the criterion is not proven by these tests. Usually `rerun` the developer step (or the one that writes the tests) and say which change the tests do not notice.
- `timed-out`, `refused` (with `detail`), `not-run` — no evidence either way. `refused` is a declaration the developer can repair (`rerun` with what `detail` says: `not-unique`, `unknown-ac`, `bad-path`, `verification-path`, `no-change`; `problem: bad-file` = the whole file). `not-run` means the engine could not run it — the last line of `log_tail` says why; when that is the tests being red without any change (twice in a row) or an environment, a rerun of the developer does not help. Only a person's `rerun` makes the engine run the same HEAD again, and only when no row was run at all — say so in your recommendation when that is the way out.
- `mutations: null` — nothing was declared. When a criterion demands such a run, that is a gap the developer can close: `rerun` the developer step and ask for the declaration.

None of these statuses decides anything by itself: you decide each criterion with them. Cite a row in `evidence` by its id (`M1 killed: …`). A criterion that only a mutation can prove and that has no `killed` row is `unmet`, unless it is honestly `manual`.

A `safety-net-proof` row of `done_gate.runs` with `flaky: true` passed on its second run: the tests were not green on the base plus the new net files, then green on the same tree. The engine does not know which test failed the first time; the PR body names that run's log for the human.

`done_gate.commits` lists the commit messages of the branch. They are the roles' words — useful to find where to look, never evidence. A red run that only a message mentions did not happen as far as you know.
