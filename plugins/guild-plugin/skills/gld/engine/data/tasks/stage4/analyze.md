**Has the Issue's premise changed since it was written?** An Issue can be overtaken: another change merged after it was written may already do what it asks, or may have changed the code it describes. Before you write acceptance criteria, check `git-history.md` in the engine folder — read-only git facts the engine collected on the recorded base: when the Issue was written, the commits since then on the paths the Issue names, where each code token the Issue quotes is found today, and which commits since then added or removed it. Then read the code at those places. Write what you found in the analysis (`## Assumptions`, or the interpretation of the Issue): "no related change since the Issue was written", or the commit(s) and what they already do, or that the code the Issue quotes is no longer there. Keep the machine field `type` the Issue's own work type: an Issue that reports a bug stays `type: bug` even when a later commit seems to have fixed it — say so in the analysis; whether it is already fixed is decided by the reproduction and by a human, not by the type. The file is an aid, not a verdict: it lists only what git shows mechanically (nothing about why), and an empty list does not prove there was no related change.
