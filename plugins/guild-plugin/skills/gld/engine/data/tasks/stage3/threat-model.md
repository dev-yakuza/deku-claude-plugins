The engine added this step from the plugin step catalog because the change touches a security surface (authentication, authorisation, secrets, personal data, an exposed endpoint or input). Model the threats of this change and write them to `docs/specs/<issue>/threat-model.md`, before the developer builds it: read `issue.md`, `analysis.md` and the code the Issue touches.

Write: the assets and trust boundaries the change crosses; per boundary the realistic threats (who, how, what they gain); for each, the mitigation the implementation must contain, stated as a checkable item the security review will look for (which input is validated where, which secret never leaves which process, which permission is checked before which call). Name what you deliberately leave out and why. A threat that only a human can accept (a residual risk, a product trade-off) is listed as such — the pull request shows it.

Never copy a real secret, key or token into the document, not even partly: it is committed and published. You model; you do not change code. Write prose in the language of the Issue, follow the repository's document rules (its markdown lint), and never use square brackets for a tag or a reference. Write only that one file.
